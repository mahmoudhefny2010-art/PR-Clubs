1. About this policy

This policy covers the MIU Student Clubs website and its club discovery, applications, event registration and attendance, student sign-in, and club administration features. It describes practices visible in the current application implementation. The university or project owner should review and confirm this draft before treating it as an authoritative privacy notice.

2. Information collected

  • Student accounts: name, email address, university ID, major, phone number and age when provided; password-derived salt and hash for password accounts; Google account subject identifier for accounts linked through Google; and last sign-in time.
  • Club applications: name, email, university ID, major, phone number, age, selected club and committee, interview slot, motivation, notes, photo reference, answers to configurable club questions, review status, ratings, and interview evaluations. Exact questions vary by club.
  • Events and attendance: name and email for event registrations; signed-in student interest by event (event opens and registration status, linked to the student account); student identity, event or booth, attendance time, and an optional note for attendance records. A keyed hash of a persistent browser identifier is also stored with check-ins to prevent repeat attendance from the same browser for the same activity.
  • Club and operational records: club member names, committee and role; club account email and password-derived data; content, sponsor and booth submissions (which may include contact details, email, phone, attachments and images); review comments and workflow history; and administrator action records that may include actor email, action details, target, timestamp, and IP address.
  • Visit analytics: a generated visitor identifier, first and last seen times, estimated device and browser names derived from the browser's User-Agent, and signed-in account type and, when signed in, account email and display name. The raw User-Agent is not stored. Administrators see a short code derived from the anonymous visitor cookie; it identifies a browser cookie, not a person or a uniquely identifiable physical device, and changes if the cookie is cleared or the browser changes. The full IP address is stored in a separate short-lived presence record, is scheduled to expire after six minutes, and is shown only in the administrator's live visitor panel; database cleanup may take additional time. A keyed hash of the address is kept for historical network-level counts. Separate administrator audit entries may store an IP address.
  • Authentication and abuse prevention: password reset token hashes and expiry, and hashed source identifiers and counters for login or recovery rate limits. Some temporary records have database expiry settings.

Published club content, event information, and some club roster details may be visible on public pages. Do not submit sensitive personal information unless a form specifically asks for it.

3. How information is collected

Information is provided through student sign-in, configurable club application forms, event registration, attendance check-in, club or administrator dashboard forms, and Ask AI questions. Student profile details entered into application forms are saved to the signed-in account for future form prefill. Google sign-in, when enabled, supplies verified account identity from Google and can create a student account. The site periodically sends a visit signal while a page is visible; the server derives the device category and network-address hash from the request.

4. How information is used

The application uses information to create and authenticate accounts, support password recovery, prefill future student forms, receive and review club applications, identify applicants, manage club membership, publish club and event content, record event registrations and attendance, administer approval workflows, and provide administrators with visit and event analytics. Signed-in event interest is used for aggregate per-event counts; the analysis view does not show student names or email addresses. Account identity and roles determine which dashboards and records are available.

5. Access and sharing

Application records are available to relevant club users and authorized administrators through protected dashboard routes. Club users can review applications for their club; committee roles receive records and actions according to assigned workflow permissions. Administrators have broader management and analytics access. Event registration and attendance details are available to the relevant club and designated review roles. Public pages expose published club, event, feed, and other approved content; some member roster details are included in site data.

The implementation sends password recovery messages through a configured SMTP service and may send uploaded images to Cloudinary when configured. Google processes identity data when Google sign-in is enabled. Database and hosting operators process application data to provide the service. Their identities, terms, and processing locations cannot be established from source code and require confirmation by the project owner.

6. Cookies and similar technologies

The site uses an HttpOnly visitor cookie with a one-year lifetime for visit analytics and an HttpOnly attendance device cookie with a one-year lifetime to prevent repeat check-ins from the same browser. Administrator and club session cookies last up to eight hours; the student session cookie persists for up to 400 days and is renewed during active use. Students can sign out from the site header, which also revokes that session on the server. Attendance scan proof and Google sign-in also use short-lived cookies. Cookies use SameSite protections, and the Secure flag is applied in production or secure contexts. The browser stores the selected visual theme in local storage. The application code contains no third-party advertising or analytics tag.

7. External services

  • OpenAI: Ask AI sends the user's question, a small number of recent user questions for context, and selected public club/event snippets to OpenAI when an API key is configured. Chat messages are not stored by this application. If no key is configured, the site-data fallback answers without sending the question to an AI provider.
  • Google Sign-In: optional student authentication when configured; Google Fonts may load the Inter typeface.
  • Cloudinary: optional image upload and hosting when configured.
  • SMTP email provider: configured delivery for password recovery; the provider is deployment-specific and not identifiable from the code.
  • Database and hosting: MongoDB is used when a database connection is configured; provider and hosting environment depend on deployment.

Each provider has its own terms and privacy information. The project owner should confirm which optional integrations are active in production.

8. Storage and retention

Application records are stored in MongoDB when configured. The code does not establish the live database provider, storage region, or a general retention schedule. Most account and application records do not have automatic expiry in the schema. Password reset, email verification, and certain rate-limit records have database expiry settings; actual expiry timing depends on the record and database TTL processing. Some application records can be deleted through available dashboard or applicant flows, but the implementation does not establish a general account deletion or automatic deletion process.

9. Security

The implementation derives password hashes with Node.js scrypt, stores reset token hashes rather than original reset tokens, signs session cookies, uses HttpOnly and SameSite cookie attributes, and applies role checks to protected dashboard routes. These measures reduce some risks but cannot guarantee complete security. The source code does not establish database encryption, live backup protection, or the operational security practices of hosting and service providers.

10. Your choices

Students can sign out at any time and can correct profile details by updating them in an application form; saved account details prefill future forms. Applicants can use the My Forms access flow to view or update an application and, where available, request its deletion using its access mechanism. Authorized club and admin dashboards include deletion actions for certain application and account records. The implementation does not provide student account deletion or self-service data export. For other access, correction, or deletion requests, contact the responsible university or project office; verified contact details are not present in this repository and must be supplied by the project owner.

11. Children's privacy

The website supports university club activities, but the code does not establish a minimum age or an age-verification process. The project owner should confirm the intended age scope and any required instructions before publication.

12. Policy updates

This page may be updated when website practices change. The application has no dedicated policy-change notification mechanism; updates may be reflected on this page. Check the “Last updated” date above.

13. Contact and publication review

The repository does not identify a verified privacy contact, responsible legal entity, governing jurisdiction, or data-protection contact. These details, plus the live database, hosting, email and image-service providers, retention schedule, and applicable user rights, must be confirmed by Misr International University or the project owner before this draft is adopted as the final policy.

This is an implementation-based draft and does not state that the service complies with any particular law.
