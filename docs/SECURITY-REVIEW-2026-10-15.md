# Security review — 15 October 2026

This is the original, pre-remediation review. See [the remediation record](SECURITY-REMEDIATION-2026-10-15.md) for implemented fixes, current verification and remaining external configuration. The old isolated vulnerability checker is historical evidence, not a current regression test.

The administration routes reject anonymous requests, but the review found authorization and authentication hardening issues that should be addressed before treating the current implementation as production ready. This review changed no application code, accounts, database records, dependencies, deployment settings or secrets.

Scope: server routes and middleware, role sessions, Google authentication, password recovery, public response shaping, uploads, frontend rendering, deployment configuration, repository exclusions and production dependency advisories. Runtime requests targeted localhost only. Production Vercel settings, edge headers and database permissions were not verified.

| Priority | Finding | Evidence and practical impact | Required action |
| --- | --- | --- | --- |
| P1 / High | Configured administrator can be replaced through local setup without authentication | `POST /api/admin/setup`, [server.js](../server.js#L6055), checks socket loopback and environment-managed credentials, but does not require an existing admin session, reject foreign origins, or disable itself in production. An isolated run of the actual handler replaced a configured mock administrator and returned 200 with no login session and a foreign Origin. | Disable web setup in production. Allow initial setup only when no administrator exists, through an explicit local bootstrap mechanism. Require authentication and reauthentication for changes to an existing administrator. Add origin protection. |
| P1 / High | Login failure counters can be cleared by signing into a different account | `loginAttemptKey`, [server.js](../server.js#L5641), identifies only the source address. Successful club, Google and administrator logins clear that shared key. An isolated test made eight guesses, with a successful-login clear between batches; the counter remained four and never locked. An attacker who has a legitimate account can repeat this pattern against another account. | Track independent counters for normalized target identity and source address, with distributed storage. A successful login should clear only that account's failures and should not clear global abuse limits. Avoid blocking an entire campus network after five unrelated failures. |
| P2 / Medium | Administrator and staff cookies do not reliably receive `Secure` behind an HTTPS proxy | `setAdminSessionCookie`, [server.js](../server.js#L753), and `setClubSessionCookie`, [server.js](../server.js#L962), depend only on `req.secure`. Unlike student cookies, they do not use the production/Vercel-aware helper. No explicit trusted-proxy configuration was found. Isolated production/proxy tests produced both cookies without Secure. | Use a consistent secure-cookie policy, require HTTPS in production, and configure proxy trust to match the actual deployment. Verify real production Set-Cookie headers after the change. |
| P2 / Medium | Public club responses include internal interview forms and sponsor attachments | [public-club-media.js](../services/public-club-media.js#L5) includes `interviewForms` and whole sponsor objects. `toPublicClubRecord` removes member rosters but retains those fields. A synthetic serialization check confirmed both internal forms and agreement links survive public shaping. Actual populated production values were not inspected. | Define explicit public fields for each nested content type. Remove interview forms from public listings; retain the existing permissioned interview-form API. Decide whether sponsor agreements are private and protect them if so. |
| P2 / Medium | Security headers and request-origin checks are inconsistent | Local HTML/redirect responses did not contain CSP, frame restrictions or nosniff. `cors()` permits `*`. Several authenticated writes check Origin, while other admin/content mutations do not. SameSite=Strict provides an existing mitigation; wildcard CORS alone does not let another origin read credentialed admin responses. | Add consistent protection for state-changing browser requests. Introduce CSP in Report-Only mode first, accounting for existing inline scripts and Google/Cloudinary/OneSignal dependencies. Add frame restrictions, nosniff, appropriate referrer policy and HTTPS/HSTS at the production edge. Restrict CORS to required origins. |
| P2 / Medium | Production dependency audit reports five affected package entries | A fresh `npm audit --omit=dev` reported 5 moderate package findings, 0 high and 0 critical: `exceljs`, `mssql`, `tedious`, `sprintf-js`, `uuid`. These are dependency-tree entries involving two underlying advisories, not five independently demonstrated exploits in the application. | Review reachable use and update compatible dependency chains. Do not run `npm audit fix --force`: the suggested ExcelJS remediation includes a major downgrade. Recheck SQL behavior and Excel exports after updates. |
| P2 / Medium | Administrative audit logging is not connected to sensitive changes | `AuditLog` is imported and counted, but no audit-log write calls were found in server, services or database runtime code for account, permission, delete or password operations. | Record actor, action, target, result and timestamp for sensitive actions, without storing passwords, session cookies, reset tokens or unnecessary personal data. Protect access and define retention. |

The setup finding is conditional on the request appearing as loopback to the application. It is directly relevant to local use and could affect a deployment behind a loopback proxy. This review did **not** establish that the current Vercel deployment exposes the same behavior. No real setup/reset request was sent.

Additional deployment and recovery work:

- Require MFA for administrators and highly privileged staff, using organizational Google policy where applicable or an appropriate second factor for password login.
- Configure an explicit strong `ADMIN_SESSION_SECRET` in production. It is absent from the current local `.env`, but the local private credential cache supplies a 64-character secret; the review did not find a missing secret in the running local application. Production configuration remains unverified.
- Local SQL configuration disables encryption and trusts the server certificate. Do not reuse that configuration for a remote production database. The existing SQL configuration code already rejects insecure settings in production/Azure mode. Use a limited application account; the live SQL privilege check timed out, so its current privileges are unknown.
- Keep an encrypted, protected backup outside the current machine/drive and test recovery periodically. Existing operations documentation states that native backups are currently local rather than off-machine copies.
- Validate attachment URLs, actual file formats and sizes on the server, including legacy sponsor uploads. Do not rely on browser `accept` attributes. Protect private applicant/speaker material according to the site's privacy policy. No successful attachment-based script execution was demonstrated.
- Add shared abuse limits to public forms, upload signatures and AI usage where appropriate. Some upload/AI limits use process-local maps and therefore are not shared across serverless instances.
- Remove accidental conversation exports from the repository and review retention of tracked data snapshots. Current `.env`, `.env.local`, private admin credentials and club credentials were not tracked, and the checked Git history did not list those paths. This was not a comprehensive historical secret scan.

Verified existing protections:

- Anonymous localhost requests to Dashboard V2 and its staff page redirected to sign-in; global administration, admin data, credentials, applications, committee requests, Dean requests and account photos rejected anonymous access with 401.
- Requests to `/.env`, `/.git/config`, `/data/admin.json` and the private dashboard template returned 404.
- Role sessions are signed, expire, and check account/session revocation state. Password hashes use scrypt. Google verification checks token identity/nonce and stored roles instead of granting arbitrary roles.
- SQL predicates use bound parameters. Speaker attachments have a separate authenticated delivery path. Feed video validation verifies Cloudinary media metadata and rejects videos in image-only content types.
- 27 selected authentication, Google identity, session and feed-validation tests passed. The three isolated setup/cookie/rate-limit checks used actual source with fake storage and no real secrets.
